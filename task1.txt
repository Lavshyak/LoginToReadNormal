0. КРАТКОЕ РЕЗЮМЕ ЗАДАЧИ (что за сервис)
---------------------------------------------------------------------
Приватный сервис с пастами (raw text) за обратным прокси nginx, всё в Docker.
Есть один администратор и создаваемые им пользователи.

Вход в систему двухступенчатый:
  1) ПЕРВИЧНЫЙ вход — единый (одинаковый для всех) URL: пользователь вводит
     ЛОГИН и ПЕРВИЧНЫЙ ПАРОЛЬ. При успехе ему генерируются ПОСТОЯННЫЙ ПАРОЛЬ
     и ПОСТОЯННАЯ СЛУЧАЙНАЯ ССЫЛКА; первичные логин/пароль перестают работать.
  2) ПОСТОЯННЫЙ вход — по выданной случайной ссылке: на ней вводится
     постоянный пароль и происходит попадание в интерфейс клиента
     НА ЭТОЙ ЖЕ ССЫЛКЕ. Пароль привязан именно к этой ссылке.

Ключевое требование безопасности: на первичном url ДО первичного входа
браузер не должен узнать о существовании каких-либо других ссылок, страниц
и api (страница «стерильная»).

Время хранится в UTC+0 и показывается в UTC+0 и в локальном поясе пользователя.

---------------------------------------------------------------------
1. РАЗБОР ТРЕБОВАНИЙ ПО ПУНКТАМ (как понял)
---------------------------------------------------------------------

(1) «Перед этим всем nginx, это все в докере.»
    -> Наружу смотрит только nginx (реверс-прокси, TLS, 80/443).
       Приложение и БД наружу не публикуются, работают во внутренней
       docker-сети. Всё поднимается через docker-compose.

(2) «Минимальное потребление ОЗУ, соответствующий выбор технологий.»
    -> Технологии с минимальным runtime: компилируемый бинарник + встроенная
       БД + server-side HTML. Подробно в разделе 2.

(3) «В начальном конфиге root url этого всего, общий (одинаковый для всех)
     первичный url, логин и первичный пароль админа.»
    -> В конфиге (.env):
         ROOT_URL         — корневой адрес сервиса;
         PRIMARY_URL_PATH — путь общего первичного url (например /login);
         ADMIN_LOGIN      — логин администратора;
         ADMIN_PRIMARY_PASSWORD — первичный пароль администратора.
       Первичный url общий для ВСЕХ: ROOT_URL + PRIMARY_URL_PATH.
       При первом старте из конфига заводится админ: username=ADMIN_LOGIN,
       primary-пароль = хеш ADMIN_PRIMARY_PASSWORD.

(4) «Админ переходит по первичному url, вводит логин и первичный пароль,
     иначе ничего не доступно. Для него генерируются новые постоянная
     случайная ссылка и постоянный пароль, первичные логин и пароль больше
     не работают, с новыми доступно всё.»
    -> Одноразовая активация:
         GET  /<primary-path>            -> форма ввода логина и пароля.
         POST /<primary-path>  верный    -> генерируются НОВЫЕ постоянная
                                            случайная ссылка (/l/<token>) и
                                            постоянный пароль; показываются
                                            ОДИН раз; первичный пароль и
                                            первичный вход ИНВАЛИДИРУЮТСЯ.
         Пока не активирован — доступ не даётся.
       «С новыми доступно всё» = полные права администратора.

(5) «На первичном url до первичного входа в аккаунт браузер не должен знать,
     что существуют какие-то другие ссылки, страницы и api.»  [НОВОЕ]
    -> Первичная страница «стерильная»:
         - self-contained: CSS/JS инлайн, НЕТ ссылок на /static, /l/* и др.;
         - нет навигации и ссылок на иные страницы;
         - форма отправляется на тот же первичный url;
         - любой запрос на неизвестный путь -> одинаковый ответ 404
           (без подсказок, без перечислений маршрутов);
         - сервер не отдаёт 401/redirect с намёками на существование api;
         - X-Robots-Tag: noindex; favicon не отдаём (или инлайн data-uri).
       Только ПОСЛЕ успешного первичного входа показываются выданные
       постоянная ссылка и постоянный пароль.

(6) «Админ может создавать нового юзера, указав юзернейм и сколько времени
     это доступно; логином юзера становится этот юзернейм, для юзера
     генерируется первичный пароль.»
    -> В админке форма: username + срок действия (TTL).
       username = логин юзера (уникален). Генерируется первичный пароль;
       первичный вход для юзера — по ОБЩЕМУ первичному url с этим логином и
       этим паролем. Через TTL доступ истекает.

(7) «Юзер должен перейти по первичному url, ввести логин (юзернейм) и
     первичный пароль; для него сгенерируются постоянная случайная ссылка и
     постоянный пароль, иначе ничего не доступно.»
    -> Тот же механизм активации, что и у админа: общий первичный url ->
       логин+первичный пароль -> постоянная случайная ссылка + постоянный
       пароль; первичные данные инвалидируются.

(8) «Постоянная случайная ссылка служит адресом интерфейса: на ней вводится
     постоянный пароль и происходит попадание в интерфейс клиента на этой же
     ссылке.»
    -> GET /l/<token>:
          - нет валидной сессии, привязанной к этому token -> форма ввода
            постоянного пароля;
          - верный постоянный пароль -> cookie + интерфейс на этом же
            /l/<token>;
       Всё приложение (дашборд, пасты, админка) расположено под этим
       префиксом /l/<token>/... и доступно только с валидной сессией.

(9) «Админ может создавать пасты (raw text), указывать Title и каким
     конкретным юзерам (или всем) они доступны, удалять пасты.»
    -> У пасты: Title, тело (raw text), автор. Аудитория: «всем» (все активные
       юзеры) либо конкретный список юзеров (checkbox). Админ умеет удалять.

(10) «При удалении пасты имеющим право просмотра юзерам показывается в
      тексте пасты [Данные удалены].»
    -> SOFT delete: паста остаётся в списке у тех, кто имел право просмотра,
       тело заменяется текстом «[Данные удалены]», контент не отдаётся.

(11) «Юзеры могут постить пасты, доступные админу (больше никому), удалять
      не могут.»
    -> Паста юзера видна только автору и админу. Создавать может, удалять — нет.

(12) «Юзер видит список паст в порядке возрастания времени.»
    -> Сортировка по created_at ASC (старые -> новые).

(13) «Время конвертируется в UTC+0, при просмотре показывается в UTC+0 и в
      часовом поясе юзера.»
    -> В БД всё в UTC (RFC3339, «Z»). В интерфейсе два значения: UTC+0 и
       локальное время (по таймзоне браузера).

(14) «Юзеру отображается, сколько паст появилось с момента его первого захода.»
    -> Запоминаем время первого захода (момент активации). Счётчик = число
       доступных юзеру паст с created_at >= first_seen_at.

(15) «Устанавливаются куки при вводе постоянного пароля.»
    -> Cookie-сессия выставляется при успешном вводе ПОСТОЯННОГО пароля на
       /l/<token> (HttpOnly, Secure, SameSite=Lax). При первичном входе cookie
       не ставим (см. допущение 6) — пользователь идёт по выданной ссылке.

(16) «Пароль не может быть валиден при переходе по ссылке другого человека
      (т.е. ссылка - логин, пароль - пароль).»
    -> На постоянном url: token (ссылка) = логин, постоянный пароль привязан
       к конкретному token -> на чужой ссылке пароль не подходит, и cookie,
       полученная на своей ссылке, на чужой игнорируется.
       (На первичном url роль «логина» играет юзернейм.)

2. ВЫБОР ТЕХНОЛОГИЙ (обоснование под «минимум ОЗУ»)
---------------------------------------------------------------------
  Слой            Выбор                        Почему / ОЗУ
  --------------- ---------------------------- -------------------------
  Reverse proxy   nginx:alpine                 ~3–8 МБ, стандарт, TLS.
  Backend         Go (net/http, stdlib)        один статический бинарник,
                                               ~10–20 МБ RSS.
  Шаблоны         html/template (stdlib)       server-side HTML, без
                                               фронтенд-фреймворка и Node.
  БД              SQLite (pure-Go, modernc)    БД = файл, нет отдельного
                  + WAL                        процесса -> ~0 МБ overhead.
  Пароли          bcrypt (golang.org/x/crypto) безопасно, дёшево по памяти.
  Статика         инлайн в шаблонах            для «стерильной» первичной
                                               страницы НЕТ внешних ссылок.
  Контейнер       multi-stage Dockerfile       образ ~15–30 МБ, без
                  (golang -> alpine/scratch)   компилятора в рантайме.

Почему Go, а не Node/Python: ~10–20 МБ RSS против ~50–100 МБ. nginx — самый
лёгкий реверс-прокси. SQLite вместо Postgres/MySQL экономит отдельный процесс.

ВАЖНО (для стерильности первичной страницы): первичный HTML самодостаточен —
CSS/JS только inline, никаких <link>/<script src>/<img src> на внутренние
endpoint'ы, чтобы до входа браузер не запрашивал и не узнавал другие пути.

Внешние зависимости (сознательно минимум):
  - modernc.org/sqlite             (SQLite без cgo)
  - golang.org/x/crypto/bcrypt     (хеширование паролей)
  Остальное — стандартная библиотека Go.

3. АРХИТЕКТУРА И DOCKER
---------------------------------------------------------------------
                Internet
                   |
              [ nginx ]   :80 (redirect->:443), :443 (TLS)
                   |  proxy_pass http://app:8080
                   v
              [ app (Go) ]  внутренний :8080, наружу не публикуется
                   |  файл БД
                   v
            [ volume: ./data/app.db (SQLite, WAL) ]

Публично доступные пути (через nginx):
  - /<primary-path>   (напр. /login)  — общий первичный вход (стерильный);
  - /l/<token>/...                     — постоянная ссылка + интерфейс.
Всё остальное -> 404 одинакового вида.

Сервисы docker-compose:
  - nginx: image nginx:alpine; ports 80/443; conf.d + сертификаты; depends_on: app.
  - app:   build (multi-stage); env из .env; volume ./data:/data;
           expose 8080 (только внутри); restart: unless-stopped.
  - сеть:  одна bridge-сеть; наружу открыт только nginx.
  - том:   ./data/app.db.

Dockerfile (multi-stage):
  FROM golang:1.22-alpine AS build -> go build -ldflags "-s -w", CGO_ENABLED=0
  FROM alpine (или scratch) + только бинарник -> минимум размера/памяти.

nginx.conf (ключевое):
  - location / -> proxy_pass http://app:8080;
  - proxy_set_header Host / X-Real-IP / X-Forwarded-For / X-Forwarded-Proto;
  - НЕ отдавать автолистинги и не добавлять собственные ссылки на ошибках
    (чтобы не нарушать стерильность первичной страницы).

4. КОНФИГУРАЦИЯ (переменные окружения / .env)
---------------------------------------------------------------------
  ROOT_URL                  — корневой адрес сервиса
  PRIMARY_URL_PATH          — путь общего первичного url (напр. /login)
  ADMIN_LOGIN               — логин администратора (напр. admin)
  ADMIN_PRIMARY_PASSWORD    — первичный пароль администратора
  SESSION_SECRET            — секрет подписи session-cookie (HMAC)
  DB_PATH                   — путь к SQLite (по умолчанию /data/app.db)
  LISTEN_ADDR               — адрес прослушивания приложения (по умолчанию :8080)
  (опц.) SESSION_TTL        — время жизни cookie-сессии
  (опц.) DEFAULT_USER_TTL   — срок доступности юзера по умолчанию

  Пример .env:
    ROOT_URL=https://paste.example.com
    PRIMARY_URL_PATH=/login
    ADMIN_LOGIN=admin
    ADMIN_PRIMARY_PASSWORD=<заданный вручную>
    SESSION_SECRET=<64 случайных байта>
    DB_PATH=/data/app.db
    LISTEN_ADDR=:8080

  Логика запуска:
    открыть БД, применить миграции, сделать seed админа: если админа ещё нет —
    создать actor(username=ADMIN_LOGIN, role=admin) с хешем ADMIN_PRIMARY_PASSWORD
    и primary_active=1. Повторный запуск ничего не пересоздаёт.

5. МОДЕЛЬ ДАННЫХ (SQLite)
---------------------------------------------------------------------
Все времена — TEXT RFC3339 UTC. Пароли — bcrypt-хеши; секрет случайной ссылки
хранится как SHA-256. «Сырые» постоянная ссылка/пароль показываются ОДИН раз.

  actors  — админ и юзеры
    id                    INTEGER PK
    username              TEXT UNIQUE            -- ЛОГИН первичного входа
    role                  TEXT                    -- 'admin' | 'user'
    created_at            TEXT  (UTC)
    first_seen_at         TEXT  (UTC, nullable)   -- первый заход (п.14)
    expires_at            TEXT  (UTC, nullable)   -- срок доступности юзера (п.6)
    is_active             INTEGER                 -- 1/0
    primary_password_hash TEXT                    -- bcrypt первичного пароля
    primary_active        INTEGER                 -- 1 пока первичный вход валиден

  permanent_links  — выданные постоянные ссылки + пароли
    id            INTEGER PK
    actor_id      INTEGER -> actors.id
    token_hash    TEXT UNIQUE                -- SHA-256 от секрета /l/<token>
    password_hash TEXT                       -- bcrypt постоянного пароля
    is_active     INTEGER                    -- 1/0 (можно отозвать)
    created_at    TEXT (UTC)

  pastes
    id            INTEGER PK
    author_id     INTEGER -> actors.id
    title         TEXT
    body          TEXT                       -- raw text (или NULL после удаления)
    audience      TEXT                       -- 'all' | 'specific' | 'admin_only'
    is_deleted    INTEGER
    deleted_at    TEXT (UTC, nullable)
    created_at    TEXT (UTC)

  paste_recipients  — при audience='specific'
    paste_id      INTEGER -> pastes.id
    actor_id      INTEGER -> actors.id
    PRIMARY KEY (paste_id, actor_id)

  sessions  (если держать список сессий для отзыва; иначе только cookie)
    id            INTEGER PK
    actor_id      INTEGER
    link_id       INTEGER                    -- привязка сессии к ссылке (п.16)
    session_hash  TEXT UNIQUE
    created_at    TEXT (UTC)
    expires_at    TEXT (UTC)

Правила видимости пасты (can_view(actor, paste)):
  - автор всегда видит свою пасту;
  - админ видит ВСЕ пасты;
  - паста админа: 'all' -> все активные юзеры; 'specific' -> перечисленные;
  - паста юзера: только автор и админ ('admin_only').

Индексы: actors(username), permanent_links(token_hash), pastes(created_at),
paste_recipients(actor_id), sessions(session_hash).

---------------------------------------------------------------------
6. АУТЕНТИФИКАЦИЯ: ПЕРВИЧНЫЙ ВХОД И ПОСТОЯННАЯ ССЫЛКА
---------------------------------------------------------------------

A. Первичный вход (общий url, стерильная страница):
   GET  {PRIMARY_URL_PATH}
       -> форма: логин + первичный пароль. Никаких ссылок/ассетов на другие
          страницы/API (см. раздел 14).
   POST {PRIMARY_URL_PATH}
       -> найти actor по username; проверить:
            - primary_password_hash (bcrypt),
            - actor.primary_active = 1,
            - не истёк expires_at (для юзера),
            - actor.is_active = 1.
          при успехе:
            * actor.primary_active = 0  -> «первичные логин/пароль больше
                                          не работают»;
            * генерируем ПОСТОЯННЫЕ: token = 32 случайных байта (base32),
              password = случайная строка (12–16 символов);
            * сохраняем permanent_links(token_hash=<SHA-256>, password_hash=
              <bcrypt>);
            * actor.first_seen_at = now(UTC) — старт счётчика (п.14);
            * показываем постоянную ссылку /l/<token> и пароль ОДИН раз;
            * cookie при этом НЕ ставим (см. допущение 6).
          при неудаче: ОБЩАЯ ошибка (без указания, есть ли такой юзер).

B. Вход по постоянной ссылке (интерфейс на этой же ссылке):
   GET  /l/<token>
       - валидная cookie, ПРИВЯЗАННАЯ к этому token -> интерфейс;
       - иначе -> форма ввода постоянного пароля.
   POST /l/<token>/unlock
       - пароль сверяется с password_hash ИМЕННО этой ссылки;
       - успех -> cookie (HttpOnly, Secure, SameSite=Lax), редирект на
                  /l/<token> (интерфейс на той же ссылке).

C. Правило п.16 («пароль не валиден на чужой ссылке»):
   - постоянный пароль хранится у конкретной ссылки -> на чужой ссылке не
     совпадёт -> отказ;
   - cookie содержит подписанные (actor_id, link_id) и принимается ТОЛЬКО
     при открытии своего /l/<token>; на чужой ссылке cookie игнорируется.

Формат cookie: base64(payload) + '.' + HMAC-SHA256(payload, SESSION_SECRET)
  payload = actor_id : link_id : expires_at
  Проверка: подпись верна И expires_at в будущем И ссылка активна И link_id
            совпадает с token из URL.

Срок (п.6): если у actor expires_at задан и now(UTC) > expires_at -> доступ
запрещён (страница «срок истёк»), cookie не помогает.

7. РОЛИ И ПРАВА
---------------------------------------------------------------------
  Действие                        | Админ | Юзер
  ------------------------------- | ----- | -------------------------------
  Первичный вход (общий url)      |  да   |  да (логин = юзернейм)
  Активация -> постоянная ссылка  |  да   |  да
  Вход по постоянной ссылке       |  да   |  да
  Создать юзера (+TTL)            |  да   |  нет
  Создать пасту                   |  да   |  да (видна только админу)
  Выбрать аудиторию пасты         |  да   |  нет (всегда admin_only)
  Удалить пасту (soft-delete)     |  да   |  нет никогда
  Видеть все пасты                |  да   |  нет

Middleware:
  requireAdmin  — /l/<token>/admin/* только для role='admin';
  requireUser   — страницы юзера;
  canViewPaste  — фильтрация списка/контента паст.

---------------------------------------------------------------------
8. ПАСТЫ: СОЗДАНИЕ / ВИДИМОСТЬ / УДАЛЕНИЕ
---------------------------------------------------------------------
Создание (админ): Title + тело (raw text, textarea) + аудитория:
    ( ) Всем
    ( ) Конкретным юзерам -> список активных юзеров (checkbox)
  -> paste(author=admin, audience='all'|'specific') + paste_recipients.

Создание (юзер): Title + тело; audience='admin_only' (виден автору и админу).

Удаление (только админ): soft-delete -> is_deleted=1, deleted_at=now, body=NULL.
  Кто имел право просмотра — по-прежнему видит пасту в списке, но тело
  отображается как «[Данные удалены]» (п.10). Строку физически не удаляем.

Рендер: тело выводится как текст (html/template экранирует), переносы строк
через CSS white-space: pre-wrap. При is_deleted вместо тела — «[Данные удалены]».

9. СПИСОК ПАСТ И ПОРЯДОК
---------------------------------------------------------------------
Видимые юзеру пасты (SQL), по возрастанию времени (п.12):
  SELECT * FROM pastes p
  WHERE p.author_id = :me
     OR p.author_id = :admin
     OR p.audience = 'all'
     OR (p.audience = 'specific' AND EXISTS(
            SELECT 1 FROM paste_recipients r
            WHERE r.paste_id = p.id AND r.actor_id = :me))
  ORDER BY p.created_at ASC;
Админ: SELECT * FROM pastes ORDER BY created_at ASC;  (все пасты)
Показываем: Title, автор, время (UTC + локальное), текст.

---------------------------------------------------------------------
10. ВРЕМЯ: ХРАНЕНИЕ UTC+0 И ОТОБРАЖЕНИЕ В ДВУХ ПОЯСАХ (п.13)
---------------------------------------------------------------------
  - В БД пишем UTC (time.Now().UTC()), формат RFC3339.
  - В HTML отдаём ISO-строку: <time datetime="2026-10-19T12:00:00Z" class="ts">…
  - Всегда видно UTC-значение (текстом).
  - Локальное время считает маленький inline JS над .ts:
        Intl.DateTimeFormat(undefined,{dateStyle:'short',timeStyle:'medium'})
  - Таймзона браузера (Intl.DateTimeFormat().resolvedOptions().timeZone)
    опционально сохраняется в cookie как подсказка (источник истины — браузер).
  Итог: «2026-10-19 12:00:00 UTC» и «19.10.2026 15:00:00 (Europe/Moscow)».

---------------------------------------------------------------------
11. СЧЁТЧИК ПАСТ С ПЕРВОГО ЗАХОДА (п.14)
---------------------------------------------------------------------
  - first_seen_at пишется при активации (первичный вход -> постоянная ссылка).
  - Число доступных юзеру паст с created_at >= first_seen_at:
      SELECT COUNT(*) FROM pastes p
      WHERE <условия видимости юзера> AND p.created_at >= :first_seen_at;
  - Бейдж на дашборде: «Новых паст с момента вашего первого захода: N».


---------------------------------------------------------------------
12. HTTP-МАРШРУТЫ (роутинг Go 1.22+, method+pattern)
---------------------------------------------------------------------
  -- первичный вход (общий url, стерильный) --
  GET  /{primary-path}                 -> форма логин + первичный пароль
  POST /{primary-path}                 -> активация -> постоянная ссылка+пароль

  -- постоянная ссылка = адрес интерфейса --
  GET  /l/{token}                      -> интерфейс ИЛИ ввод постоянного пароля
  POST /l/{token}/unlock               -> проверка постоянного пароля, cookie
  POST /l/{token}/logout               -> сброс cookie

  -- интерфейс (под тем же /l/{token}) --
  GET  /l/{token}/pastes               -> список паст (ASC) + счётчик новых
  GET  /l/{token}/pastes/{id}          -> просмотр пасты
  POST /l/{token}/pastes               -> создать пасту
  GET  /l/{token}/admin/users          -> список юзеров (статус/срок)
  POST /l/{token}/admin/users          -> создать юзера (username + TTL) ->
                                          показать первичный пароль один раз
  POST /l/{token}/admin/pastes         -> создать пасту (title/body/аудитория)
  POST /l/{token}/admin/pastes/{id}/delete -> soft-delete пасты

  Авторизация: middleware берёт token из URL -> проверяет cookie (подпись +
  совпадение link_id + срок) -> кладёт actor в context. Все страницы под
  /l/{token}/* требуют её. Неизвестный/чужой путь -> 404 одинакового вида.

13. UI-СТРАНИЦЫ (серверные шаблоны html/template)
---------------------------------------------------------------------
  primary_login.html     — стерильная форма логин+пароль (inline CSS/JS,
                           без ссылок на другие страницы/API).
  credentials.html       — показ выданных постоянной ссылки и постоянного
                           пароля ОДИН раз (кнопки «скопировать»).
  link_unlock.html       — ввод постоянного пароля на /l/<token>.
  layout_app.html        — каркас интерфейса (живёт под /l/<token>).
  dashboard.html         — дашборд (админ: пасты+юзеры; юзер: пасты+счётчик).
  paste_new.html         — создание пасты (админ: аудитория; юзер: admin_only).
  paste_view.html        — просмотр (UTC + локальное; удалённое -> placeholder).
  users.html             — управление юзерами (создание с TTL, список).
  expired.html / error.html — срок истёк / ошибки доступа.

Минимум JS: конвертация времени в локальный пояс; (опц.) запоминание таймзоны.

14. БЕЗОПАСНОСТЬ
---------------------------------------------------------------------
  - Стерильность первичной страницы (п.5):
       * HTML самодостаточен: CSS/JS inline, НЕТ ссылок на /static, /l/*,
         иную страницу или api;
       * нет навигации; форма POST на тот же первичный url;
       * неизвестные пути -> одинаковый 404 без подсказок и перечислений;
       * не отдаём 401/redirect, раскрывающих существование api;
       * X-Robots-Tag: noindex; favicon не отдаём (или inline data-uri).
  - Пароли: bcrypt (cost 10–12). Секрет ссылки: 32 случайных байта.
  - Cookie: HttpOnly + Secure + SameSite=Lax; подпись HMAC-SHA256.
  - Привязка сессии к ссылке (п.16) — ключевое свойство авторизации.
  - Constant-time сравнение секретов; активность ссылки проверяется в БД.
  - Инвалидация первичного входа после активации.
  - XSS: html/template экранирует; тело пасты — как текст (pre-wrap).
  - CSRF: SameSite=Lax + одноразовый CSRF-токен в формах POST.
  - Rate-limit попыток пароля (простой in-memory счётчик).
  - Наружу — только nginx; app слушает только внутреннюю сеть.

16. ПРОВЕРКА (сценарии приёмки)
---------------------------------------------------------------------
  [ ] Наружу торчит только nginx; всё в Docker.
  [ ] Конфиг содержит root url, общий первичный url, логин/первичный пароль админа.
  [ ] На первичном url до входа браузер НЕ видит ссылок/страниц/api:
      нет <link>/<script src>/<img src> на внутренние пути; форма — на тот же url.
  [ ] Любой неизвестный путь до входа -> одинаковый 404 (без подсказок).
  [ ] Админ: первичный url + логин/первичный пароль -> новые постоянная
      случайная ссылка + постоянный пароль; СТАРЫЕ логин/пароль не работают;
      по новым есть всё.
  [ ] Админ создаёт юзера (username + TTL) -> выдан первичный пароль
      (логин = юзернейм).
  [ ] Юзер: первичный url + логин/пароль -> постоянная ссылка + постоянный
      пароль; на этой ссылке ввод постоянного пароля -> интерфейс на этой же ссылке.
  [ ] Просроченный по TTL юзер -> доступа нет.
  [ ] Админ создаёт пасту «всем» и «конкретным» -> видна ровно тем; удаление ->
      у имеющих доступ тело «[Данные удалены]».
  [ ] Юзер постит пасту -> доступна админу и автору, больше никому; удалять не может.
  [ ] Список паст у юзера — по возрастанию времени.
  [ ] Время хранится в UTC; показываются UTC+0 И локальный пояс.
  [ ] Счётчик «сколько паст появилось с первого захода» корректен.
  [ ] Cookie выставляется при вводе постоянного пароля.
  [ ] Пароль НЕ валиден на чужой ссылке; cookie чужака не даёт доступ.

17. ДОПУЩЕНИЯ И ОТКРЫТЫЕ ВОПРОСЫ (требуют подтверждения)
---------------------------------------------------------------------
  1. Стек: Go + SQLite + nginx (под «минимум ОЗУ»).
  2. Один админ; создаётся из конфига, юзеры — админом.
  3. «Сколько времени доступно» для юзера = TTL: (a) от выдачи — по умолчанию;
     (b) от первого входа. При истечении — полный запрет доступа (в т.ч. на
     первичном url и по постоянной ссылке).
  4. Логин админа и юзеров — юзернейм (уникален). Юзернейм неизменяем.
  5. Пасту, созданную юзером, видит и сам автор (не только админ).
  6. Cookie НЕ ставится при первичном входе (по ТЗ — «при вводе постоянного
     пароля»): после активации пользователь идёт по выданной ссылке и вводит
     постоянный пароль. Если хотим авто-вход — легко добавить.
  7. «Всем» = всем активным юзерам (плюс автор-админ).
  8. Тело удалённой пасты стирается (body=NULL), факт удаления и адресаты
     сохраняются — чтобы placeholder видели только имевшие доступ.
  9. Первичный url — единый путь (PRIMARY_URL_PATH); его можно замаскировать
     произвольным сегментом (напр. /x7f2), чтобы сам факт наличия входа не
     бросался в глаза.
