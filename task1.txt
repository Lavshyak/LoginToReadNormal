0. КРАТКОЕ РЕЗЮМЕ ЗАДАЧИ (что за сервис)
---------------------------------------------------------------------
Приватный «read-сервис» с пастами (raw text) за обратным прокси nginx,
всё в Docker. Есть один администратор и создаваемые им пользователи.
Доступ к системе возможен ТОЛЬКО по персональным секретным ссылкам
(ссылка = логин) + пароль (пароль = пароль). Сначала у каждого
«первичная» ссылка+пароль (bootstrap, одноразовые), после первого входа
они превращаются в «постоянные» ссылку+пароль, старые перестают работать.
Админ и юзеры создают/видят пасты согласно правам, время хранится в UTC+0
и показывается в UTC+0 и в локальном поясе пользователя.

---------------------------------------------------------------------
1. РАЗБОР ТРЕБОВАНИЙ ПО ПУНКТАМ (как понял)
---------------------------------------------------------------------

(1) «Перед этим всем nginx, это все в докере.»
    -> Наружу смотрит только nginx (реверс-прокси, TLS, порты 80/443).
       Приложение и БД не публикуются наружу, работают во внутренней
       docker-сети. Всё поднимается через docker-compose.

(2) «Минимальное потребление ОЗУ, соответствующий выбор технологий.»
    -> Выбираем технологии с наименьшим runtime-потреблением:
       компилируемый бинарник + встроенная БД + server-side HTML.
       Подробнее в разделе 2.

(3) «В начальном конфиге первичный url и первичный пароль для админа,
     root url этого всего.»
    -> В конфиге (.env / config-файл) задаются:
         ROOT_URL              — корневой адрес сервиса (точка входа);
         ADMIN_PRIMARY_TOKEN   — секрет первичной ссылки админа;
         ADMIN_PRIMARY_PASSWORD— первичный пароль админа.
       При первом старте из этих значений заводится bootstrap-запись админа.
       Полная первичная ссылка = ROOT_URL + /l/<ADMIN_PRIMARY_TOKEN>.

(4) «Админ переходит по первичной ссылке, вводит первичный пароль,
     иначе ничего не доступно. Для него генерируются новые постоянные
     ссылка и пароль, старые больше не работают, с новыми доступно всё.»
    -> Одноразовый bootstrap:
         GET  первичная ссылка -> форма ввода первичного пароля.
         POST верный пароль     -> генерируются НОВЫЕ постоянная ссылка+пароль,
                                   показываются один раз, первичные
                                   ИНВАЛИДИРУЮТСЯ (становятся недействительны).
         Пока первичный пароль не введён — никакой функциональности нет
         (все остальные разделы отдают 401/redirect).
       «С новыми доступно всё» = полные права администратора.

(5) «Админ может создавать нового юзера, указав юзернейм и сколько времени
     это доступно, для юзера генерируются первичные ссылка и первичный пароль.»
    -> В админке форма: username + срок действия (TTL, напр. 1h/1d/дата).
       Генерируются первичная ссылка и первичный пароль конкретного юзера.

(6) «Юзер должен перейти по ссылке, ввести пароль, для него сгенерируются
     постоянные ссылка и пароль, иначе ничего не доступно.»
    -> Тот же bootstrap-механизм, что и у админа: первичная ссылка+пароль
       юзера -> после ввода пароля генерируются постоянные ссылка+пароль,
       первичные инвалидируются. Без пароля/просрочки — доступа нет.

(7) «Админ может создавать пасты (raw text), указывать Title и каким
     конкретным юзерам (или всем) они доступны, удалять пасты.»
    -> У пасты есть Title, тело (raw text), автор.
       При создании выбирается аудитория:
         - «всем» (все активные юзеры),
         - либо конкретный список юзеров (checkbox-список).
       Админ может удалять пасты.

(8) «При удалении пасты имеющим право просмотра юзерам показывается
     в тексте пасты [Данные удалены].»
    -> Удаление «мягкое» (soft-delete): паста остаётся в списке у тех, кто
       имел право просмотра, но её тело заменяется текстом
       «[Данные удалены]», а контент физически не отдаётся.

(9) «Юзеры могут постить пасты, доступные админу (больше никому),
     удалять не могут.»
    -> Паста, созданная юзером, видна только ему самому и админу.
       Юзер может создавать пасты, но НЕ может удалять (ни свои, ни чужие).

(10) «Юзер видит список паст в порядке возрастания времени.»
    -> Список паст, доступных юзеру, сортируется по created_at ASC
       (старые -> новые).

(11) «Время конвертируется в UTC+0, при просмотре показывается в UTC+0
      и в часовом поясе юзера.»
    -> В БД всё хранится в UTC (ISO-8601, «Z»).
       В интерфейсе для каждого времени показываются ДВА значения:
         - UTC (UTC+0);
         - локальное время пользователя (по таймзоне браузера).

(12) «Юзеру отображается, сколько паст появилось с момента его первого захода.»
    -> Запоминается время «первого захода» (активации аккаунта).
       Счётчик = число доступных юзеру паст, созданных >= времени первого
       захода. Показывается в интерфейсе юзера.

(13) «Устанавливаются куки при вводе постоянного пароля.»
    -> Успешный ввод постоянного пароля выставляет session-cookie
       (HttpOnly, Secure, SameSite=Lax) — далее авторизация по cookie,
       без повторного ввода пароля до истечения сессии.

(14) «Пароль не может быть валиден при переходе по ссылке другого человека
      (т.е. ссылка - логин, пароль - пароль).»
    -> Ссылка = идентификатор (логин), пароль — только к СВОЕЙ ссылке.
       Сессия/пароль жёстко привязаны к token (ссылке): cookie, полученная
       по своей ссылке, не даёт доступа по чужой ссылке; ввод своего пароля
       на чужой ссылке отклоняется.

2. ВЫБОР ТЕХНОЛОГИЙ (обоснование под «минимум ОЗУ»)
---------------------------------------------------------------------
Ключевая идея: не тащить тяжёлый runtime и отдельный сервер БД.

  Слой            Выбор                        Почему / ОЗУ
  --------------- ---------------------------- -------------------------
  Reverse proxy   nginx:alpine                 ~3–8 МБ, стандарт, TLS.
  Backend         Go (net/http, stdlib)        один статический бинарник,
                                               ~10–20 МБ RSS, без VM и
                                               тяжёлых зависимостей.
  Шаблоны         html/template (stdlib)       server-side HTML, без
                                               фронтенд-фреймворка и Node.
  БД              SQLite (pure-Go драйвер      БД = файл, нет отдельного
                  modernc.org/sqlite, WAL)     процесса -> ~0 МБ overhead.
  Пароли          bcrypt (golang.org/x/crypto) безопасно, дёшево по памяти.
  Статика         embed.FS + отдача nginx      1 маленький CSS, минимум JS.
  Контейнер       multi-stage Dockerfile       образ ~15–30 МБ, без
                  (golang -> alpine/scratch)   компилятора в рантайме.

Почему Go, а не Node/Python: при той же функциональности Go-бинарник
даёт ~10–20 МБ RSS против ~50–100 МБ у Node/Python-серверов. nginx —
самый лёгкий и предсказуемый реверс-прокси. SQLite вместо PostgreSQL/MySQL
экономит отдельный процесс на 100+ МБ ОЗУ.

Интерфейс — минималистичный HTML, без внешних CDN и тяжёлых JS-библиотек.
JavaScript используется ТОЛЬКО для перевода времени из UTC в локальный пояс.

Внешние зависимости (сознательно минимум):
  - modernc.org/sqlite             (SQLite без cgo)
  - golang.org/x/crypto/bcrypt     (хеширование паролей)
  Остальное — стандартная библиотека Go.

3. АРХИТЕКТУРА И DOCKER
---------------------------------------------------------------------
                Internet
                   |
              [ nginx ]   :80 (redirect->:443), :443 (TLS)
                   |  proxy_pass http://app:8080
                   v
              [ app (Go) ]  внутренний :8080, наружу не публикуется
                   |  файл БД
                   v
            [ volume: ./data/app.db (SQLite, WAL) ]

Сервисы docker-compose:
  - nginx: image nginx:alpine; ports 80/443; монтирует conf.d и сертификаты;
           depends_on: app.
  - app:   build (multi-stage); env из .env; volume ./data:/data;
           expose 8080 (только внутри сети); restart: unless-stopped.
  - сеть:  одна bridge-сеть; наружу открыт только nginx.
  - том:   ./data/app.db (персистентность SQLite).

Dockerfile (multi-stage):
  FROM golang:1.22-alpine AS build
     -> go build -ldflags "-s -w", CGO_ENABLED=0
  FROM alpine (или scratch) + только бинарник
     -> минимальный размер и низкое потребление памяти.

nginx.conf (ключевое):
  - location / -> proxy_pass http://app:8080;
  - proxy_set_header Host / X-Real-IP / X-Forwarded-For / X-Forwarded-Proto;
  - статика может отдаваться nginx напрямую.

4. КОНФИГУРАЦИЯ (переменные окружения / .env)
---------------------------------------------------------------------
  ROOT_URL                 — корневой адрес сервиса (например https://paste.example.com)
  ADMIN_PRIMARY_TOKEN      — секрет первичной ссылки админа (генерируется при первичной установке)
  ADMIN_PRIMARY_PASSWORD   — первичный пароль админа
  SESSION_SECRET           — секрет для подписи session-cookie (HMAC)
  DB_PATH                  — путь к файлу SQLite (по умолчанию /data/app.db)
  LISTEN_ADDR              — адрес прослушивания приложения (по умолчанию :8080)
  (опц.) SESSION_TTL       — время жизни cookie-сессии

  Пример .env:
    ROOT_URL=https://paste.example.com
    ADMIN_PRIMARY_TOKEN=<32 случайных байта base32>
    ADMIN_PRIMARY_PASSWORD=<заданный вручную>
    SESSION_SECRET=<64 случайных байта>
    DB_PATH=/data/app.db
    LISTEN_ADDR=:8080

  Логика запуска:
    при старте приложение открывает БД, применяет миграции и делает
    «seed»: если админа ещё нет — создаёт actor(role=admin) + primary-token
    из ADMIN_PRIMARY_TOKEN с хешем ADMIN_PRIMARY_PASSWORD.
    Повторный запуск ничего не пересоздаёт (primary уже неактивен после ввода).

5. МОДЕЛЬ ДАННЫХ (SQLite)
---------------------------------------------------------------------
Все времена — TEXT в формате RFC3339 UTC (например 2026-10-19T12:00:00Z).
Пароли хранятся в виде bcrypt-хешей, секреты ссылок — как SHA-256(токен);
«сырые» значения ссылок/паролей показываются пользователю ОДИН раз.

  actors  — админ и юзеры
    id            INTEGER PK
    username      TEXT                       -- 'admin' или заданный
    role          TEXT                       -- 'admin' | 'user'
    created_at    TEXT  (UTC)
    first_seen_at TEXT  (UTC, nullable)      -- время первого захода (п.12)
    expires_at    TEXT  (UTC, nullable)      -- срок доступности юзера (п.5)
    is_active     INTEGER                    -- 1/0

  tokens  — ссылки (первичные и постоянные)
    id            INTEGER PK
    actor_id      INTEGER -> actors.id
    kind          TEXT                       -- 'primary' | 'permanent'
    token_hash    TEXT UNIQUE                -- SHA-256 от секрета в URL
    password_hash TEXT                       -- bcrypt (пароль этого токена)
    is_active     INTEGER                    -- первичный гасится после ввода
    created_at    TEXT (UTC)
    expires_at    TEXT (UTC, nullable)       -- срок первичной ссылки юзера

  pastes
    id            INTEGER PK
    author_id     INTEGER -> actors.id
    title         TEXT
    body          TEXT                       -- raw text (или NULL после удаления)
    audience      TEXT                       -- 'all' | 'specific' | 'admin_only'
    is_deleted    INTEGER                    -- 1 при soft-delete
    deleted_at    TEXT (UTC, nullable)
    created_at    TEXT (UTC)

  paste_recipients  — при audience='specific': кому видна паста
    paste_id      INTEGER -> pastes.id
    actor_id      INTEGER -> actors.id
    PRIMARY KEY (paste_id, actor_id)

  sessions  (опционально, если держать список сессий для отзыва)
    id            INTEGER PK
    actor_id      INTEGER
    token_id      INTEGER                    -- привязка сессии к ссылке (п.14)
    session_hash  TEXT UNIQUE
    created_at    TEXT (UTC)
    expires_at    TEXT (UTC)

Правила видимости пасты (can_view(actor, paste)):
  - автор всегда видит свою пасту;
  - админ видит ВСЕ пасты;
  - паста админа:
       audience='all'      -> видят все активные юзеры;
       audience='specific' -> видят только перечисленные в paste_recipients;
  - паста юзера: только автор и админ (audience='admin_only').

Индексы: pastes(created_at), paste_recipients(actor_id),
tokens(token_hash), sessions(session_hash).

6. АУТЕНТИФИКАЦИЯ: ПЕРВИЧНЫЕ И ПОСТОЯННЫЕ ССЫЛКИ
---------------------------------------------------------------------
Общий URL входа:  GET /l/<token>   (token = секрет из ссылки = «логин»)

Состояния token:
  - primary + is_active=1   -> экран «введите первичный пароль»;
  - permanent + is_active=1 -> если валидной сессии нет -> экран ввода
                               постоянного пароля; иначе рабочий экран.

Поток bootstrap (одинаков для админа и юзера):
  1. GET /l/<primary-token>          -> форма ввода первичного пароля.
  2. POST /l/<primary-token>/unlock  -> сверяем bcrypt с password_hash.
     - неверно -> ошибка, доступа нет;
     - верно:
         * гасим первичный токен (is_active=0) -> «старые больше не работают»;
         * генерируем ПОСТОЯННЫЕ ссылку и пароль (crypto/rand):
             token  = 32 случайных байта (base32/base62);
             пароль = случайная строка (12–16 символов);
         * сохраняем новый token(kind=permanent) + bcrypt(пароль);
         * записываем actors.first_seen_at = now(UTC) — старт счётчика (п.12);
         * показываем постоянную ссылку и пароль ОДИН раз;
         * устанавливаем session-cookie (п.13).

Поток входа по постоянной ссылке:
  1. GET /l/<permanent-token>
       - валидная cookie, ПРИВЯЗАННАЯ к этому же token -> рабочий экран;
       - иначе -> форма ввода постоянного пароля.
  2. POST /l/<permanent-token>/unlock
       - пароль сверяется с password_hash ИМЕННО этого token;
       - успех -> выставляем session-cookie (HttpOnly, Secure, SameSite=Lax)
                  и переходим на рабочий экран.

Правило п.14 («пароль не валиден на чужой ссылке»):
  - пароль хранится отдельно у каждого token, поэтому ввод своего пароля
    на чужой ссылке не совпадёт -> отказ;
  - cookie содержит подписанные (actor_id, token_id) и принимается ТОЛЬКО
    при открытии /l/<своего токена>; на чужой ссылке cookie игнорируется
    -> снова запрос пароля.

Формат cookie: base64(payload) + '.' + HMAC-SHA256(payload, SESSION_SECRET)
  payload = actor_id : token_id : expires_at
  Проверка: подпись верна И expires_at в будущем И token активен И
            token_id совпадает с токеном из URL.

Проверка срока (п.5): при каждом запросе, если у actor есть expires_at и
now(UTC) > expires_at -> доступ запрещён (страница «срок истёк»), cookie
не помогает.

---------------------------------------------------------------------
8. ПАСТЫ: СОЗДАНИЕ / ВИДИМОСТЬ / УДАЛЕНИЕ
---------------------------------------------------------------------
Создание (админ):
  Форма: Title + тело (textarea, raw text) + выбор аудитории:
    ( ) Всем
    ( ) Конкретным юзерам  -> список активных юзеров (checkbox)
  Сохраняем paste(author=admin, audience='all'|'specific'),
  при 'specific' пишем строки в paste_recipients.

Создание (юзер):
  Форма: Title + тело. audience='admin_only'.
  Видят: автор + админ. Больше никто (п.9).

Удаление (только админ):
  POST /admin/paste/<id>/delete -> SOFT delete:
    is_deleted=1, deleted_at=now(UTC), body=NULL.
  Кто имел право просмотра — продолжает видеть пасту в списке,
  но её тело отображается как «[Данные удалены]» (п.8).
  Физическое удаление строки НЕ делаем (чтобы placeholder был виден
  ровно тем, кому паста была доступна).

Рендер контента:
  body выводится как обычный текст (html/template экранирует),
  переносы строк — через CSS white-space: pre-wrap (без HTML-парсинга).
  Если is_deleted: вместо body рендерим «[Данные удалены]» (серым/курсивом).

9. СПИСОК ПАСТ И ПОРЯДОК
---------------------------------------------------------------------
Запрос списка (SQL, по возрастанию времени — п.10):
  SELECT * FROM pastes
  WHERE is_deleted=0 OR <видимые пользователю>          -- для юзера
    AND ( author_id = :me
          OR author_id = :admin
          OR (audience='all')
          OR (audience='specific' AND EXISTS(
                SELECT 1 FROM paste_recipients r
                WHERE r.paste_id=pastes.id AND r.actor_id=:me)) )
  ORDER BY created_at ASC;

  Админ: SELECT ... FROM pastes ORDER BY created_at ASC;  (все пасты)

Показываем: Title, автор, время (UTC + локальное), превью/полный текст.

---------------------------------------------------------------------
10. ВРЕМЯ: ХРАНЕНИЕ UTC+0 И ОТОБРАЖЕНИЕ В ДВУХ ПОЯСАХ (п.11)
---------------------------------------------------------------------
  - В БД пишем всегда UTC (time.Now().UTC()), формат RFC3339.
  - В HTML отдаём ISO-строку в атрибут, напр.:
        <time datetime="2026-10-19T12:00:00Z" class="ts">…</time>
  - На странице всегда видно UTC-значение (текстом).
  - Локальное время считает маленький inline JS:
        Intl.DateTimeFormat(undefined, {dateStyle:'short',timeStyle:'medium'})
        над всеми .ts, беря datetime.
  - Таймзона браузера (Intl.DateTimeFormat().resolvedOptions().timeZone)
    опционально сохраняется в cookie, чтобы сервер мог подписать/показать
    её как подсказку (но источник истины — браузер при просмотре).
  Итог: для каждого времени видим «2026-10-19 12:00:00 UTC» и
  «19.10.2026 15:00:00 (Europe/Moscow)».


---------------------------------------------------------------------
11. СЧЁТЧИК ПАСТ С ПЕРВОГО ЗАХОДА (п.12)
---------------------------------------------------------------------
  - first_seen_at пишется в момент успешной активации (primary->permanent).
  - Для юзера считаем число доступных ему паст с created_at >= first_seen_at:
      SELECT COUNT(*) FROM pastes p
      WHERE <условия видимости юзера>
        AND p.created_at >= :first_seen_at;
  - Показываем бейдж на дашборде: «Новых паст с момента вашего первого
    захода: N».

---------------------------------------------------------------------
12. HTTP-МАРШРУТЫ (роутинг Go 1.22+, method+pattern)
---------------------------------------------------------------------
  GET  /                        -> редирект на вход/инфо-страницу
  GET  /l/{token}               -> экран входа (primary или permanent)
  POST /l/{token}/unlock        -> проверка пароля, cookie, редирект

  -- админ (только role=admin) --
  GET  /admin                   -> дашборд: список паст + список юзеров
  POST /admin/users             -> создать юзера (username, TTL) ->
                                   показать первичную ссылку+пароль один раз
  GET  /admin/users             -> список юзеров (статус/срок)
  POST /admin/pastes            -> создать пасту (title, body, audience, recipients)
  POST /admin/pastes/{id}/delete -> soft-delete пасты

  -- юзер (role=user) --
  GET  /me                      -> список паст (ASC) + счётчик новых
  POST /me/pastes               -> создать пасту (title, body) -> admin_only

  GET  /static/*                -> статика (или отдаёт nginx)
  POST /logout                  -> сброс cookie

  Авторизация: middleware достаёт token из URL -> проверяет cookie
  (подпись + совпадение token_id + срок) -> кладёт actor в context.
  Все страницы вне /l/{token} требуют валидной сессии.

14. БЕЗОПАСНОСТЬ
---------------------------------------------------------------------
  - Пароли: bcrypt (cost 10–12).  Секреты ссылок: 32 случайных байта.
  - Cookie: HttpOnly + Secure + SameSite=Lax; подпись HMAC-SHA256.
  - Привязка сессии к token (п.14) — ключевое свойство авторизации.
  - Constant-time сравнение там, где сравниваем секреты напрямую.
  - Активный токен проверяется в БД на каждом запросе — можно отозвать.
  - Инвалидация первичных токенов после использования.
  - XSS: html/template экранирует; тело пасты — как текст (pre-wrap).
  - CSRF: SameSite=Lax + одноразовый CSRF-токен в формах (POST).
  - Ограничение частоты попыток пароля (простой in-memory счётчик).
  - Наружу — только nginx; app слушает только внутреннюю сеть.

16. ПРОВЕРКА (сценарии приёмки)
---------------------------------------------------------------------
  [ ] Наружу торчит только nginx; всё в Docker.
  [ ] В конфиге есть root url + первичные url/пароль админа.
  [ ] Первичная ссылка админа без пароля -> доступа нет.
  [ ] Ввод первичного пароля -> новые постоянные ссылка+пароль; старая
      ссылка/пароль больше НЕ работают; по новой — полный доступ.
  [ ] Админ создаёт юзера (username + TTL) -> выданы первичные ссылка+пароль.
  [ ] Юзер: первичная ссылка+пароль -> постоянные; иначе доступа нет.
  [ ] Просроченный по TTL юзер -> доступа нет.
  [ ] Админ создаёт пасту (Title + текст) «всем» и «конкретным» -> видна
      ровно тем; удаление -> у имеющих доступ тело «[Данные удалены]».
  [ ] Юзер постит пасту -> доступна админу и автору, больше никому;
      удалить не может.
  [ ] Список паст у юзера — по возрастанию времени.
  [ ] Время хранится в UTC; показываются UTC+0 И локальный пояс.
  [ ] Счётчик «сколько паст появилось с первого захода» корректен.
  [ ] Cookie выставляется после ввода постоянного пароля.
  [ ] Пароль НЕ валиден на чужой ссылке; cookie чужака не даёт доступ.

17. ДОПУЩЕНИЯ И ОТКРЫТЫЕ ВОПРОСЫ (требуют подтверждения)
---------------------------------------------------------------------
  1. Стек: Go + SQLite + nginx (выбран под «минимум ОЗУ»). Если нужен
     другой язык — легко заменить backend, схема БД остаётся.
  2. Один админ. Админ создаётся из конфига, юзеры — админом.
  3. «Сколько времени доступно» для юзера = TTL: (a) от создания — доступ
     истекает через N времени после выдачи; (b) от первого входа.
     По умолчанию берём (a). При истечении — полный запрет доступа.
  4. Пасту, созданную юзером, видит и сам автор (не только админ).
  5. «Всем» = всем активным юзерам (плюс администратор-автор).
  6. Ссылка на пасту: список + отдельная страница просмотра.
  7. Cookie выставляется и при активации, и при вводе постоянного пароля
     (спецификация упоминает «при вводе постоянного пароля»).
  8. Хранение тела удалённой пасты: тело стирается (body=NULL), факт
     удаления и адресаты сохраняются — чтобы placeholder видели только
     те, у кого был доступ.
