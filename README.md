коротко: пользователь активирует свой аккаунт в (например) /login (с помощью временного логина и пароля), ему выдется постоянная случайная ссылка и постоянный случайный пароль по которой интерфейс с просмотром raw text паст от админа (паста может быть доступна всем пользователям или только конкретным). Пользователь может постить пасты, доступные только ему и админу. У админа примерно та же логика входа. Минимум ОЗУ, расчитано на несколько десятков пользователей и несколько десятков паст. В /login браузер ничего не знает о других страницах и API.

# LoginToReadNormal

Приватный сервис с пастами (raw text) за обратным прокси **nginx**, всё в **Docker**.
Один администратор + создаваемые им пользователи. Двухступенчатый вход:
сначала единый «первичный» URL (логин + первичный пароль), затем — выданная
постоянная случайная ссылка с постоянным паролем.

## Стек (выбран под минимум ОЗУ)

| Слой            | Технология                                  | Почему |
|-----------------|---------------------------------------------|--------|
| Reverse proxy   | `nginx:alpine` + TLS                        | ~несколько МБ, стандарт |
| Backend         | Go 1.23, только `net/http` (роутинг 1.22+)  | один статический бинарник, ~10–20 МБ RSS |
| Шаблоны         | `html/template` (server-side HTML)          | без Node и фронтенд-фреймворков |
| БД              | SQLite (`modernc.org/sqlite`, без cgo) + WAL| БД = файл, нет отдельного процесса |
| Пароли          | `golang.org/x/crypto/bcrypt`                | безопасно и дёшево |
| Статика         | инлайн в шаблонах                           | стерильная первичная страница без внешних ссылок |
| Контейнер       | multi-stage Dockerfile (`golang` → `alpine`) | маленький образ без компилятора в рантайме |

Внешних зависимостей всего две: `modernc.org/sqlite` и `golang.org/x/crypto`.

## Архитектура

```
Internet
   |
[ nginx ]  :80 -> redirect :443 (TLS)
   |  proxy_pass http://app:8080
   v
[ app (Go) ]  внутренний :8080, наружу НЕ публикуется
   |
[ volume ./data/app.db (SQLite, WAL) ]
```

Публично доступны только:
- `ROOT_URL` + `PRIMARY_URL_PATH` — общий первичный вход (стерильный);
- `/l/<token>` и всё под ним — постоянная ссылка и интерфейс.

Любой другой путь → **одинаковый** 404 без подсказок.

## Конфигурация (`.env`)

| Переменная | Назначение |
|-----------|------------|
| `ROOT_URL` | корневой адрес сервиса (например `https://paste.example.com`) |
| `PRIMARY_URL_PATH` | путь общего первичного URL (например `/login` или маскировка `/x7f2`) |
| `ADMIN_LOGIN` | логин администратора |
| `ADMIN_PRIMARY_PASSWORD` | первичный пароль администратора (только для первого seed) |
| `SESSION_SECRET` | секрет подписи cookie (HMAC-SHA256), ≥ 16 байт |
| `DB_PATH` | путь к SQLite (по умолчанию `/data/app.db`) |
| `LISTEN_ADDR` | адрес прослушивания (по умолчанию `:8080`) |
| `SESSION_TTL` | время жизни cookie-сессии (по умолчанию `12h`) |
| `DEFAULT_USER_TTL` | окно активации нового юзера по умолчанию (`720h`) |
| `COOKIE_SECURE` | флаг `Secure` у cookie; `false` только для локального http |

Скопируйте `.env.example` в `.env` и задайте значения:

```bash
cp .env.example .env
# Сгенерировать секрет:
openssl rand -hex 32
```

## Запуск

```bash
mkdir -p data
docker compose up -d --build
```

- `https://<host>/<PRIMARY_URL_PATH>` — вход (логин/первичный пароль админа из `.env`).
- При первом старте создаётся администратор с `primary_active = 1`.
- nginx сам генерирует самоподписанный сертификат при первом запуске
  (положите свои `fullchain.pem` + `privkey.pem` в `./nginx/certs`, чтобы использовать их).

Остановить: `docker compose down` (данные останутся в `./data`).

> **Linux:** bind-mount `./data` принадлежит root; приложение работает под uid `10001`.
> Выполните `sudo chown -R 10001:10001 data` перед первым запуском.

## Сценарий использования

1. **Админ**: открывает `PRIMARY_URL_PATH`, вводит `ADMIN_LOGIN` + `ADMIN_PRIMARY_PASSWORD`.
   Получает **один раз** постоянную ссылку `/l/<token>` и постоянный пароль.
   Первичные логин/пароль перестают работать.
2. **Админ** в разделе «Пользователи» создаёт юзера (юзернейм + **окно активации**
   в днях). Логин юзера = юзернейм, для него генерируется **первичный пароль**
   (показывается один раз). Юзер должен активироваться в течение этого срока;
   **после активации доступ бессрочный**. Там же админ может **удалить юзера**:
   аккаунт отключается, постоянная ссылка отзывается, юзер пропадает из списка
   и из выбора аудитории (его пасты у админа остаются).
3. **Юзер**: тот же первичный URL → логин + первичный пароль → постоянная ссылка + постоянный пароль.
4. **Вход по постоянной ссылке**: на `/l/<token>` вводится постоянный пароль →
   выставляется cookie → интерфейс на этой же ссылке.
5. **Пасты**: админ создаёт пасты с заголовком и аудиторией («всем» / конкретные юзеры)
   и может их удалять (soft-delete → `[Данные удалены]`). Юзеры создают пасты,
   видимые только автору и админу, удалять не могут. Список — **по убыванию времени
   создания** (новые сверху), **все пасты показаны развёрнуто** (тело видно прямо
   в списке, без перехода). Для пасты, выданной конкретным юзерам, админ видит
   **список получателей** (на странице пасты и в списке).
6. **Время**: в БД хранится UTC; в UI показывается UTC+0 и локальное время браузера.
7. **Счётчик**: юзеру показывается, сколько доступных ему паст появилось
   **с момента его предыдущего захода** (при самом первом заходе — с момента активации).
   Значение фиксируется на время сессии и обновляется при следующем входе по ссылке.

## Безопасность

- **Стерильная первичная страница**: HTML самодостаточен (CSS/JS инлайн), нет
  `<link>`, `<script src>`, `<img src>`, нет навигации и ссылок на другие страницы/API;
  форма POST-ится на тот же URL; `X-Robots-Tag: noindex`; favicon не отдаётся.
- **Одинаковый 404** для всех неизвестных путей (включая неверные токены и попытки
  path-cleaning вида `//login`) — никаких подсказок о существовании маршрутов.
- **Пароли**: bcrypt (cost 11). **Секрет ссылки**: 32 случайных байта (base32), в БД — SHA-256.
- **Cookie**: `HttpOnly`, `Secure`, `SameSite=Lax`, подпись HMAC-SHA256; payload =
  `actor_id:link_id:expires`; cookie привязана к конкретной ссылке и по `Path`
  ограничена `/l/<token>`.
- **Привязка «ссылка = логин, пароль = пароль»**: постоянный пароль хранится у конкретной
  ссылки; на чужой ссылке он не подходит, а cookie, полученная на своей ссылке, на чужой
  игнорируется (проверяется `link_id` из URL).
- **Инвалидация первичного входа** после активации (`primary_active = 0`).
- **CSRF**: double-submit токен во всех POST-формах. **Rate-limit** попыток пароля (in-memory).
- **XSS**: `html/template` экранирует; тело пасты выводится как текст (`white-space: pre-wrap`).
- Наружу смотрит только nginx; контейнер `app` не публикует порты.

## Обновление на сервере (без потери данных)

Схема БД обновляется автоматически при старте приложения (`db.Migrate`): он
только добавляет недостающие колонки и выполняет идемпотентные правки данных.
Таблицы не пересоздаются, строки не удаляются — пароли, ссылки, пасты и юзеры
сохраняются.

Миграция смены поведения «срок = окно активации» устроена безопасно:

- у всех, кто **уже активировался** (`first_seen_at IS NOT NULL`), дедлайн
  обнуляется → такие юзеры становятся **бессрочными**, никого не отключает;
- у **ещё не активированных** юзеров окно активации сохраняется без изменений;
- админ не затрагивается.

Порядок обновления:

```bash
# 1. (рекомендуется) бэкап: файлы WAL копируем вместе с базой
docker compose stop
tar -czf backup-$(date +%F-%H%M).tgz data/
# 2. подтянуть код и пересобрать — миграция применится при старте
docker compose up -d --build
# 3. убедиться, что всё поднялось и админ не пересоздавался
docker compose logs app --tail 20
```

Проверить результат можно в админке: у ранее активированных юзеров в колонке
«Активировать до» будет «бессрочно», статус — «активен (бессрочно)».

Откат: вернуть `data/` из архива и запустить предыдущую версию кода — миграция
неразрушающая, старый код работает с этой же базой.

## Заметки и принятые решения

- Список сессий в БД не ведётся: cookie **stateless** (подпись HMAC + срок).
  Отзыв = истечение срока или отключение ссылки/актора.
- При первичном входе **сессионная** cookie не ставится (по ТЗ cookie ставится при вводе
  постоянного пароля); ставится только CSRF-cookie.
- Срок юзера (`actors.expires_at`) — это **только окно активации**: юзер должен
  активироваться до этого момента. При активации `expires_at` обнуляется, и
  аккаунт становится **бессрочным** (`NULL` = «никогда не истекает»). Неактивированный
  юзер, у которого окно прошло, потерять доступ не может (у него и нет ссылки),
  но и активироваться уже не сможет.
- Тело удалённой пасты стирается (`body = NULL`), факт удаления и адресаты сохраняются —
  чтобы `[Данные удалены]` видели только те, у кого был доступ.
- `PRIMARY_URL_PATH` можно замаскировать произвольным сегментом (например `/x7f2`),
  чтобы сам факт наличия входа не бросался в глаза.
- Удаление юзера — «мягкое»: строка актора сохраняется (`deleted_at`, `is_active = 0`),
  постоянные ссылки переводятся в `is_active = 0`. Это отзывает доступ, но сохраняет
  пасты, которые юзер отправлял админу. Юзернейм удалённого юзера остаётся занятым
  (ограничение уникальности сохраняется), поэтому повторно создать такой же логин нельзя —
  при необходимости удалите/переименуйте запись в БД вручную.
- Счётчик «новых паст» привязан к началу сессии: при вводе постоянного пароля
  берётся базовая метка времени (предыдущий заход или активация) и кладётся в
  подписанную cookie (4-е поле payload), а `last_seen_at` сдвигается на текущий момент.
  Так счётчик не «сбрасывается» от перезагрузки страницы внутри одной сессии.
